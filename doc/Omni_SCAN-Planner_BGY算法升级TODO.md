# Omni SCAN-Planner 量产升级路线与 BGY 算法吸收 TODO

## 1. 文档目的

本文给出 Omni SCAN-Planner 从当前工程化研究版本走向可量产版本的完整路线，
并规划如何分阶段吸收 BGY 版本中经过代码核验、对模式 3（参考路径导航）有
明确价值的算法能力，同时保持 Omni 当前的工程结构、消息接口和真机安全链。

目标不是把 BGY 仓库整体合并进 Omni，也不是把
`class1_scanplanner_flow.cpp`、`planner_manager.cpp` 等大文件直接复制过来。
目标是将可复用的算法思想拆成职责单一、可测试、可回滚的 Omni 模块。

BGY 算法吸收只是本路线的一部分。量产还必须同步解决实时资源上限、地图和定位
健康、执行端失联停车、地形可通行性、动态障碍、故障注入、配置治理、制品发布和
长期数据回归。本文后半部分使用四条并行工作流和产品里程碑组织这些工作。

本文的主要输入基线：

- Omni：`ros2-community` 分支，本轮核验提交 `a5beac162a51`；
- BGY：`/data/robot/SCAN-Planner` 的 `heng_ros2` 分支，本轮核验提交
  `acca120aa51b`；
- 重点对比范围：参考路径进度、局部目标、直通走廊、A* 避障区间、局部轨迹与
  全局进度映射、平滑回接、最终轨迹验收。

### 1.1 代码核验结论与证据边界

截至本文本轮审查，BGY 当前实现可以作为算法原型和测试场景来源，不能作为可直接
合入的量产基线：

- BGY 的全局进度实现确实包含拓扑窗口、方向/横向门限、运动里程预算和闭环 seam
  gate；局部轨迹映射也使用有序 guide 投影，而不是无约束最近点匹配；
- BGY 的阻塞区间和锚定 A* 能限制避障只修改局部受阻段，这一策略具有明确迁移价值；
- BGY 当前提交在本轮 x86 复测中可完成相关包编译，但存在 VLA、缺少返回值、未使用
  参数和符号比较等 warning；
- 本轮执行的 94 个 C++ gtest 中 93 个通过、1 个失败；失败项为保守机身包络 A* 的
  搜索时限测试，说明现有计时器还不是端到端硬 deadline；
- 历史文档中的测试通过数只能作为当时提交的记录，不能替代当前提交、当前平台和
  当前参数下的复测；DDS E2E、rosbag、HIL 和真机仍需按本文 Gate 单独验证。

因此本文中的“吸收”统一表示：迁移经过核验的约束、状态语义和测试思想，并按 Omni
接口重新实现。除非同时给出来源、许可证、平台复测和安全验收证据，不得把“BGY 已有
实现”表述为“Omni 已具备量产能力”。

## 2. 必须保留的 Omni 基线

下面能力已经优于 BGY，升级期间不得回退：

- 保留 `SCANReplanFSM`、`SCANPlannerManager`、`GridMap`、`BsplineOptimizer`
  的分层，不引入编号式类名和超大单体 FSM；
- 保留点云与传感器位姿的 `ApproximateTime` 同步、时间差检查和 frame 严格检查；
- 保留 odom、地图 freshness watchdog；
- 保留 `PlannerHeartbeat`、轨迹双身份校验和控制器 fail-closed 行为；
- 保留带 `std_msgs/Header` 的新版 `scan_planner_msgs/msg/Bspline`；
- 保留 `LocalTrajectoryTracker` 的真实空间进度和控制器一致性；
- 保留 TF 转换、有限值检查和现有局部有界循环；在此基础上补齐规划级 deadline、
  输入/搜索/采样硬上限和平台资源预算；
- 保留模式 1、模式 2 的现有行为；新算法默认只影响模式 3；
- 保留仿真、真机、action server 和现有 launch 接口。

任何阶段若需要破坏上述边界，必须先单独提交设计说明，不能夹在功能提交中完成。

## 3. BGY 中计划吸收的算法贡献

### 3.1 优先吸收

1. 局部轨迹弧长到全局路线弧长的单调映射；
2. 优先沿当前实际局部轨迹更新全局进度，失败时保持进度，不跳回空间近邻分支；
3. 机身有宽高的直通走廊检测，以及阻塞区间输出；
4. 直行与避障两个规划分支及其迟滞切换；
5. 只对阻塞区间构造 A* 避障 guide，其余区间保持全局路径顺序；
6. 当前位姿到已确认路线进度的五次偏移渐变参考；该参考只作为候选 seed，不能单独
   证明最终轨迹全局 C²；
7. 对 direct 和 avoidance 候选实施分区明确的最大参考偏离硬验收；这是 Omni 要求，
   不能视为 BGY 所有分支已经完整实现；
8. 回接段最大曲率验收与扩大回接距离重试；
9. 开放路径、闭环路径和指定圈数的统一进度表示；
10. 对应的纯算法单测、集成测试和录包回归场景。

### 3.2 暂不吸收

- BGY 的旧版 `Bspline.msg`；
- 异步“最新 lidar pose + 最新 cloud”的地图输入方式；
- `frames.strict_check=false` 后继续使用数值的兼容策略；
- `codegroup_scanplanner` 命名空间和 `class1/class2/class4` 类命名；
- 整条全局路径以 0.20 m 间距全部送入 dense minimum-snap 求解；
- 依赖仓库外 `0_source_env` 的部署结构；
- 关闭或绕过最终安全检查的 legacy 分支；
- 为了复现 BGY 行为而修改模式 1、模式 2。

## 4. 目标架构

升级后的模式 3 数据流应为：

```text
上游全局 Path
  -> ReferenceRoute（永久、不可变、弧长参数化）
  -> ReferenceProgressTracker（全局任务进度）
       ^
       | LocalRouteProgressMap
       |（当前实际局部轨迹 local_s -> route_s）
       |
当前 odom -> LocalTrajectoryTracker

ReferenceRoute 当前进度到局部目标
  -> MergeReferenceBuilder（当前位置平滑接入路线）
  -> DirectCorridorEvaluator
       |- 通畅 -> FOLLOW_REFERENCE
       `- 阻塞 -> CollisionIntervals -> A* Guide Builder
  -> LocalTrajectoryPlanner
  -> TrajectoryAcceptanceValidator
       |- 连续机身碰撞
       |- 避障区外参考偏离
       |- 回接曲率
       |- 动力学与有限值
       `- 生成 LocalRouteProgressMap
  -> 原子提交新轨迹、映射、分支状态和 heartbeat
```

上述整条候选链必须共享同一个只读 `PlanningContext`：固定任务身份、定位样本、
`map_revision`、TF/配置快照和 absolute steady-clock `PlanDeadline`。deadline 不是
诊断计时；走廊采样、A* 邻居展开/包络查询、优化器和最终曲线验收的内部循环均必须
主动检查并有各自的数量硬上限。

关键原则：候选轨迹生成期间不修改当前有效轨迹、任务进度或分支状态。所有检查通过后
一次性提交；失败时继续持有上一条仍安全的轨迹，或者明确撤销运动授权。

走廊检测只负责快速选择分支和生成阻塞区间，不构成最终安全证明。无论 direct 还是
avoidance 分支，提交前都必须对最终实际 B-spline 执行连续机身扫掠碰撞、参考偏离、
曲率和动力学硬验收。

## 5. 数据模型与代码规范

### 5.1 建议新增类型

在 `src/planner/plan_manage/include/plan_manage/` 下新增：

- `reference_route.h/.cpp`
  - 保存去重后的原始折线；
  - 保存累计弧长；
  - 支持 `pointAt()`、`tangentAt()`、`sampleRange()`；
  - 支持开放路线和闭环路线的 unwrapped arc length；
  - 负责保留原始拐点，防止等距采样跨过 U 形/直角顶点。
- `route_progress_tracker.h/.cpp`
  - 从现有 `ReferencePathTracker` 演进；
  - 管理运动预算、方向约束、拓扑窗口和圈数；
  - 不依赖 ROS、GridMap 或 PlannerManager。
- `local_route_progress_map.h/.cpp`
  - 表示 `local_s -> route_s` 的单调映射；
  - 支持校验、插值、投影和新轨迹切换初始化。
- `merge_reference_builder.h/.cpp`
  - 构造当前位置到路线的五次偏移渐变 seed；
  - 返回明确的 `MergeReferenceResult`，不修改外部状态。
- `planning_branch.h`
  - 定义 `FOLLOW_REFERENCE`、`AVOID_OBSTACLE`；
  - 定义分支选择输入、结果和诊断原因。
- `trajectory_acceptance_validator.h/.cpp`
  - 汇总参考偏离、回接曲率、进度映射和有限值检查；
  - 地图碰撞检查可通过只读接口注入，避免依赖整个 FSM。
- `planning_context.h`
  - 保存一次候选规划使用的 route/task identity、定位、配置和 TF 快照；
  - 持有只读 map view 与 `map_revision`；
  - 持有贯穿全部规划阶段的 absolute steady-clock `PlanDeadline`；
  - 不拥有或修改当前已提交轨迹。

在 `src/planner/plan_env/include/plan_env/` 下新增：

- `direct_corridor.h/.cpp`
  - 纯几何采样和阻塞区间聚合；
  - GridMap 只提供 occupancy 查询接口；
  - 不在 `grid_map.cpp` 中堆积全部路径策略。

### 5.2 类型设计要求

- 弧长统一使用米，命名必须带 `_s` 或 `_arc_length`；
- 全局任务进度使用 `route_s`，闭环累计进度使用 `unwrapped_route_s`；
- 当前局部轨迹进度使用 `local_s`；
- 禁止用同一个 `double progress` 同时表示时间和空间弧长；
- 路径上的采样点应同时携带位置、切向和弧长，避免调用者重复查找；
- 结果存在失败可能时返回结构化状态，不使用“空 vector 同时代表无障碍和失败”；
- 所有候选对象先在局部变量中构造，检查通过后再 `commit`；
- 参数必须在加载时校验有限值、正负范围以及参数间关系；
- 算法库不读取 ROS 参数、不发布 topic、不打印 `cout`；日志留在接入层；
- 新增公共头文件使用 `scan_planner` 命名空间、统一 include guard 和 Doxygen 注释；
- 不增加新的全局 `using namespace`；
- 新代码通过 `-Wall -Wextra -Wpedantic`，不允许新增 warning；
- 不允许无界循环；采样数量必须有由路径长度和硬上限共同决定的预算；
- deadline 必须向内层循环传播，不能只在 A*/优化器外层记录耗时；
- 不允许在规划热路径构造与路径点数平方或立方增长的无上限 dense 矩阵。

### 5.3 来源与提交规范

- 优先根据行为和测试重新实现，不直接复制 BGY 的大段代码；
- 如必须复用具体实现，先核验上游许可证和版权，再保留来源说明；
- 每个阶段独立提交，禁止形成类似 BGY 的“两万行单提交”；
- 一个提交只完成一种职责：数据结构、算法、接入、测试、参数或文档；
- 每个阶段结束时，模式 1/2 和模式 3 原行为都必须可以通过参数回退。

### 5.4 第一版算法选型决定

| 问题 | 第一版选择 | 暂不作为第一版主方案 | 原因 |
| --- | --- | --- | --- |
| 永久路线进度 | 有界窗口内的单调投影 + heading/lateral gate + movement credit | 全局任意最近点、无界动态规划匹配 | 前者确定、可解释、线性/局部复杂度，足以覆盖 U 形、自交和静止抖动 |
| 局部轨迹映射 | 实际 B-spline 空间采样 + 有序 guide + 入口/出口锚点 + 局部弧长比例额度 | 对每个采样点独立投影永久路线 | 避免绕障、自交和并行段跳支路，并使重规划切换语义明确 |
| merge seed | 五次 offset fade，避开原始折角，最终曲线硬验收 | 直接宣称全局 C²；第一版即引入复杂 clothoid/G² 求解器 | 先以小型纯模块获得主要收益；若曲率指标不达标再以数据驱动升级连接器 |
| 直通判断 | 基于 Omni 机身模型和 yaw sweep 的保守走廊 | BGY 矩形走廊作为最终安全证明 | 走廊适合快速分支，最终安全必须由实际曲线连续扫掠确认 |
| 静态避障 | route_s 锚定阻塞区间的 bounded A* | 起点到局部目标的自由最短路、整条全局 dense 求解 | 最大限度保持任务拓扑并缩小搜索范围 |
| 分支迟滞 | steady-clock 持续时间 + 不同 map revision + 当前轨迹复检 | 仅按 planner 回调次数计数 | 行为不依赖规划频率，也不把同一地图重复计算当成新证据 |
| 候选提交 | 不可变输入快照 + 局部 CandidatePlan + 全硬验收后原子 commit | 生成期间修改当前 LocalTrajData/branch/id | 失败、超时和取消不会产生半更新状态 |

第一版 anchored A* 仍可使用 XY 搜索和受控 Z 插值，但只准入近平面静态 ODD。需要处理
坡度、台阶、坑洞和支撑面时，应升级为带 traversability 代价的状态格或等价搜索，不能
仅靠增加三维体素碰撞检查宣称四足可通行。

## 8. 第一轮开发范围与启用边界

第一轮不要直接接入全部 BGY 功能。首先完成 M0/M1 的可测量和安全底座：

1. 固定基线指标；
2. 明确 ODD、输入输出契约、故障语义和 x86/Orin/S100 分平台资源预算；
3. 建立贯穿式 `PlanDeadline`、输入/搜索/采样硬上限和规划线程隔离；
4. 建立 `PlanningContext`、只读地图 revision 和 `CandidatePlan` 原子提交；
5. 完成断流、超时、任务替换、地图变化和 planner 失联的故障注入；
6. 通过 Gate M1。

Phase 1～4 的纯算法模块可以与安全底座并行开发和单测，但在 Gate M1 通过前：

- 不接管默认运行时行为；
- 不打开真机运动功能开关；
- 不允许绕过旧安全链发布新候选；
- 不把算法单测通过等同于模式 3 集成完成。

Gate M1 通过后，再按 `ReferenceRoute -> RouteProgressTracker ->
LocalRouteProgressMap -> MergeReferenceBuilder` 的顺序逐个接入，每项使用独立功能开关
和固定录包对照。这样既允许提前开发纯算法，又不会让新行为先于 deadline、地图快照和
原子提交进入运行链。

## 11. 四条并行工作流

后续不要把所有任务排成单条算法流水线。量产路线分成四条工作流，并在每个产品
里程碑汇合。

### 工作流 A：路线与避障算法

对应本文 Phase 0～12：

```text
参考路线模型
  -> 拓扑进度
  -> 局部/全局进度映射
  -> 平滑回接
  -> 直通走廊
  -> 区间 A*
  -> 最终贴合/曲率验收
  -> 多圈任务
```

责任边界：提升“走哪条路、如何绕、如何回来”，不负责掩盖输入健康和底盘安全问题。

### 工作流 B：实时与功能安全

```text
ODD/故障矩阵
  -> deadline 与资源预算
  -> callback/规划线程隔离
  -> 地图/定位健康
  -> 轨迹租约与执行端 watchdog
  -> 故障注入安全证明
```

责任边界：保证任何候选算法失败、超时或进程失联时，机器人不会继续盲走。

### 工作流 C：可通行性与动态环境

```text
地面分割/高程
  -> traversability
  -> 四足能力约束
  -> 动态障碍跟踪
  -> 时空碰撞
  -> 恢复行为
```

责任边界：从“不会撞到体素”升级为“真实四足机器人能够安全通过”。

### 工作流 D：验证、发布与运营

```text
需求编号/基线指标
  -> 单测/属性测试
  -> 集成/端到端
  -> rosbag/仿真/HIL
  -> 故障注入/长稳
  -> CI/制品/SBOM
  -> 灰度/现场数据回归
```

责任边界：让每项能力可证明、可复现、可发布、可回滚。

## 12. 产品里程碑路线

下面里程碑是推荐实施顺序。里程碑不是按“代码写完”判断，而是按 Gate 是否通过。

### M0：可测量基线

#### 实施内容

- 工作流 A：完成 Phase 0；
- 工作流 B：完成 ODD、接口契约、故障矩阵和资源预算初稿；
- 工作流 D：建立固定 rosbag、指标工具和 CI 基线。

#### Gate M0

- [ ] 当前 Omni 在固定场景中的成功率、偏离、碰撞、耗时和急停次数可重复测量；
- [ ] BGY 对照报告明确区分 build、gtest、DDS E2E、rosbag、HIL 和真机证据，不使用
  单一“测试通过数”代替分层结论；
- [ ] 测试可主动识别进度跳段、地图过期、planner失联和过期轨迹复用；
- [ ] 所有后续需求都有编号和负责人/状态；
- [ ] 没有“只靠 RViz 看起来正常”的验收项。

### M1：安全底座

#### 实施内容

- 工作流 B：deadline、资源上限、规划线程隔离、地图/定位健康、运动租约；
- 工作流 D：故障注入框架、ASan/UBSan、基础长稳测试；
- 工作流 A：只允许无行为变化的 `ReferenceRoute` 重构，以及未接入运行时的纯算法
  模块和单测。

#### Gate M1

- [ ] kill planner、断 cloud、断 odom、断 DDS 后，底盘在规定时间内停车；
- [ ] 任何规划调用都在硬 deadline 内返回；
- [ ] 人工注入单次昂贵 occupancy/包络查询时，内层算法仍在同一 absolute deadline
  内退出；
- [ ] 输入回调和 heartbeat 不因优化器阻塞而超时；
- [ ] 超长/异常输入不会 OOM、死循环或发布 NaN；
- [ ] 地图和定位恢复前不会重新授权运动；
- [ ] 候选生成失败、超时、任务替换和地图失效不会污染当前轨迹、进度、branch、
  optimizer 状态或身份计数；
- [ ] 至少完成 8 小时 HIL/仿真长稳，无持续内存增长。

### M2：可靠路线执行

#### 实施内容

- 工作流 A：在 Gate M1 后按独立功能开关接入并完成 Phase 1～4；
- 工作流 B：任务身份贯穿 route、trajectory、heartbeat；
- 工作流 D：U 形、自交、闭环和轨迹切换回归。

#### Gate M2

- [ ] 静止、抖动、重复重规划均不能推动全局任务进度；
- [ ] U 形、平行往返和 8 字路线无错误跳段；
- [ ] 绕障或跟踪偏离期间，route_s 由实际局部轨迹映射连续推进；
- [ ] 新旧轨迹切换无进度回退或突跳；
- [ ] 平滑接入不修改永久路线长度和任务拓扑；
- [ ] 五次偏移渐变只作为 seed；所有提交轨迹仍通过最终 B-spline 曲率和动力学验收；
- [ ] 模式 1/2 无回归。

### M3：受约束的静态避障与回接

#### 实施内容

- 工作流 A：完成 Phase 5～9；
- 工作流 B：候选地图 revision、过时候选取消、最终轨迹原子提交；
- 工作流 D：多障碍、窄通道、死胡同和最终曲线验收回归。

#### Gate M3

- [ ] A*只修改有锚点的阻塞区间；
- [ ] direct corridor 只用于分支选择；direct/avoidance 最终轨迹均通过连续机身扫掠
  碰撞检查；
- [ ] 避障区外最终曲线偏离不超过上限；
- [ ] direct 分支以及 avoidance 的各语义区间均满足对应硬参考偏离上限；
- [ ] 回接曲率和动力学约束满足四足底盘能力；
- [ ] 最终实际 B-spline 通过连续机身碰撞检查；
- [ ] 障碍消失后按 steady-clock 时间和不同 map revision 共同确认，分支迟滞稳定且不
  随规划频率变化；
- [ ] 规划 P99 和 max 不超过 M1 的资源预算；
- [ ] 旧安全轨迹保持与新候选提交之间不存在半更新状态。

### M4：复杂地形与动态环境

#### 实施内容

- 工作流 C：traversability、四足能力约束、动态障碍、时空碰撞和恢复行为；
- 工作流 A：完成多圈闭环；
- 工作流 D：地形台架、动态障碍仿真和 HIL。

#### Gate M4

- [ ] 在 ODD 范围内正确识别坡地、台阶、坑洞和不可支撑区域；
- [ ] 几何无碰撞但不可通行的路径不会被提交；
- [ ] 动态横穿和迎面障碍在停车距离内被预测和处理；
- [ ] 恢复动作有界、可取消且不产生振荡；
- [ ] 闭环多圈不误计圈、不跨缝跳进度；
- [ ] 超出 ODD 时明确停车/失败，不尝试“尽量走过去”。

### M5：量产候选版本

#### 实施内容

- 工作流 D：完整测试矩阵、制品、SBOM、升级/回滚、现场数据闭环；
- 四条工作流完成参数冻结和文档收口。

#### Gate M5

- [ ] amd64/aarch64 Release 构建可重复；
- [ ] ASan/UBSan/TSAN 和静态检查无阻断问题；
- [ ] 24 小时仿真/HIL与 72 小时长稳计划通过既定门槛；
- [ ] 所有 P0/P1 故障注入符合故障响应矩阵；
- [ ] ODD 内场景达到目标成功率、碰撞率和性能指标；
- [ ] 二进制、配置、地图和录包可完整复现任一测试结果；
- [ ] 支持签名制品升级和一键回滚；
- [ ] 真机版本不存在未登记的外部环境、vendor或脚本依赖；
- [ ] 发布评审签署后才能将新算法开关改为默认启用。

## 13. 测试矩阵与发布准入

### 13.1 测试层级

| 层级 | 目标 | 每次提交 | 每夜 | 发布前 |
| --- | --- | ---: | ---: | ---: |
| 纯算法 gtest | 几何、进度、映射、曲率 | 是 | 是 | 是 |
| 属性/fuzz | 异常路径和消息健壮性 | 精简 | 是 | 长时 |
| 模块集成 | GridMap、A*、Manager、Optimizer | 相关改动 | 是 | 是 |
| ROS launch/E2E | QoS、TF、时间、任务状态 | 相关改动 | 是 | 是 |
| rosbag 回归 | 真实输入行为指标 | 核心改动 | 全量 | 全量 |
| 仿真场景 | 障碍、地形、动态目标 | 核心改动 | 全量 | 全量 |
| HIL | 真计算平台、RMW、watchdog | 否 | 计划任务 | 是 |
| 真机封闭场 | 真实运动与停车距离 | 否 | 否 | 是 |
| 长稳 | 内存、延迟、状态泄漏 | 否 | 8h | 24/72h |

### 13.2 自动阻断条件

任一条件满足时禁止合并或发布：

- 新增编译 warning、静态检查高风险问题或 sanitizer 错误；
- 任何测试发布 NaN/Inf 或非单调 route_s；
- deadline 超时后仍提交候选轨迹；
- 任一内层循环突破已批准 absolute deadline，或通过分阶段重新计时规避总预算；
- 输入失联后控制器继续复用旧运动命令；
- 地图/定位不健康时 `motion_allowed=true`；
- 轨迹、progress map、branch和heartbeat身份不一致；
- 最终曲线碰撞、曲率/动力学超限，或 direct/avoidance 任一受控区间参考偏离超限；
- P99 或最大规划时间超过已批准预算；
- 内存持续增长或队列无界积压；
- 模式 1/2 的既有回归测试失败；
- 新依赖没有许可证、版本和校验信息。

### 13.3 指标建议

每个版本至少保存：

- 任务成功率、取消率、失败原因分布；
- 碰撞和最小障碍距离；
- 全局 route_s 单调性和最大单帧跳跃；
- 参考路径最大、均方、P95偏离；
- 最大曲率、曲率变化率、速度和加速度超限；
- 规划成功率、重试次数和分支切换次数；
- 规划 P50/P95/P99/max；
- odom、cloud、map、heartbeat age；
- 急停次数、停车延迟和停车距离；
- CPU、RSS、分配峰值和 callback 延迟；
- 8/24/72小时运行中的资源趋势。

## 14. 当前最清晰的执行顺序

如果从现在开始实施，推荐按下面顺序推进，不要直接从走廊/A*开始：

### 第 1 批：先让系统可测、可停、可超时退出

1. 完成 Phase 0 基线指标和固定录包；
2. 写 ODD、接口契约、故障响应矩阵初稿；
3. 为 x86、Orin、S100 确定第一版规划周期、CPU、内存、路线点数、搜索节点数和采样
   上限；
4. 引入贯穿式 `PlanDeadline`，确保所有内层循环和重试共享一个绝对截止时间；
5. 将同步规划与输入/heartbeat callback 隔离；
6. 建立不可变 `PlanningContext`、地图 revision 和局部 `CandidatePlan`；
7. 实现候选验证后的原子提交，失败不得修改当前轨迹、进度和身份；
8. 完成地图/定位 freshness、执行端轨迹租约和过时候选取消；
9. 建立 kill/断流/延迟/时间回跳/慢地图查询故障注入测试；
10. 通过 Gate M1。

### 第 2 批：解决路线进度和回接的根问题

1. 抽离不可变 `ReferenceRoute`；
2. 升级拓扑/朝向受限的 `RouteProgressTracker`；
3. 实现 `LocalRouteProgressMap`；
4. 明确避障入口/出口锚点和“任务进度额度”语义，确保一个 odom 样本只消费一次；
5. 统一 action、heartbeat 和 FSM 使用确认后的 `route_s`；
6. 实现五次偏移渐变 `MergeReferenceBuilder`，只作为候选 seed；
7. 用最终实际 B-spline 验证曲率、航向、速度和加速度；
8. 跑完 U 形、自交、闭环和轨迹切换回归；
9. 通过 Gate M2。

### 第 3 批：升级静态避障质量

1. 先完善 direct/avoidance 共用的最终曲线硬验收；
2. 实现复用 Omni 双圆柱/扫掠模型的直通走廊，并明确它只是分支粗检；
3. 引入按 steady-clock 时间和不同 map revision 确认的直行/避障迟滞；
4. 只对阻塞区间运行 deadline-aware A* 并构造 composite guide；
5. 升级 reference cost 的单调对应；
6. 增加分区参考偏离和回接曲率硬验收及有界重试；
7. 在慢包络查询、多障碍和过期地图场景复核性能预算与原子提交；
8. 通过 Gate M3。

### 第 4 批：补足四足量产能力

1. 建立 traversability layer；
2. 统一 Planner/Controller 的四足运动能力模型；
3. 加入动态障碍短时预测和时空碰撞；
4. 完成有界恢复状态机；
5. 实现明确的闭环多圈任务语义；
6. 通过 Gate M4。

### 第 5 批：形成可发布产品

1. 完成参数 schema、配置版本和 preflight；
2. 完成 CI、交叉平台构建、sanitizer、SBOM和制品签名；
3. 完成 rosbag、仿真、HIL、封闭场和长稳矩阵；
4. 建立现场故障录包和回归数据闭环；
5. 冻结量产参数并完成发布/回滚演练；
6. 通过 Gate M5。

## 15. Definition of Done

任何 TODO 只有同时满足以下条件才能标记完成：

- 需求和失败语义已写清楚；
- 代码职责单一，未扩大单体 FSM/Manager；
- 参数有单位、范围、默认值和关系校验；
- 正常、边界和失败路径有自动化测试；
- 有明确的时间和内存上限；
- 候选失败不会污染当前有效状态；
- 日志、指标和错误码足够定位问题；
- 文档与实际接口同步；
- 对应 CI 和录包回归通过；
- 涉及运动安全时完成 HIL/真机封闭场验证；
- 可以通过独立提交或功能开关安全回滚。

“代码已经写完”“RViz 看起来正常”或“现场跑过一次”均不满足完成定义。
